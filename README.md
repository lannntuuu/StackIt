# StackIt

个人服用记录。Windows 桌面应用，导入 `记录.md`，立刻看到三年规律；之后随手记、随时导出。

## 快速开始

```powershell
# 构建
dotnet build native/StackIt.App -c Release

# 签名发布到 native/dist（首次先跑 new-cert.ps1 生成证书，见下文「代码签名」）
#   本机连不上 nuget.org 加 -NoRestore；要单文件 exe 加 -SelfContained
cd native
powershell -ExecutionPolicy Bypass -File .\new-cert.ps1   # 只跑一次
powershell -ExecutionPolicy Bypass -File .\publish.ps1    # 每次发布都跑
cd ..

# 运行
native\dist\StackIt.App.exe

# 回归验证（数据一致性 + 界面耗时）
powershell -NoProfile -ExecutionPolicy Bypass -File verify/native.ps1
```

> **发布前先关掉正在运行的 App。** 它锁着 `dist` 里的 dll，`publish` 会连报
> 4 个 `MSB3021/MSB3027`（"文件正被另一进程使用"）。这个错误容易被当成
> NuGet 问题而误判。发完对一下 `StackIt.Core.dll` 的时间戳再测——
> **测旧二进制等于没测**。
>
> **别用 `& exe` 调用 StackIt.App。** 它是 GUI 子系统程序（WinExe），
> PowerShell 拿不到它的 stdout 和退出码，会得到假输出（曾因此读到"0 条事件"）。
> 取它的输出要用 `cmd /c "... > log 2> err"`。
>
> **改 `.ps1` 后要确认 UTF-8 BOM 还在。** PowerShell 5.1 不带 BOM 时按 GBK 读脚本，
> 中文注释会把语法读坏（报"字符串缺少终止符"），而报错位置看起来毫不相关。
>
> `--no-restore` 是必要的：这台机器连不上 nuget.org，restore 阶段会 `NU1301`。
> 要免安装的单文件 exe，在能联网的机器上跑
> `dotnet publish -c Release -r win-x64 --self-contained`。

首次打开是空的。到**数据**页 →「选择 记录.md 导入」，或用命令行直接灌：

```powershell
dotnet run --project native/StackIt.Core -c Release -- seed 记录.md
```

导入时会弹窗告诉你解析出多少条、周一校验过没过、有没有未识别的 token。

## 三个页面

| 页面 | 作用 |
|---|---|
| **统计** | 默认页。每周用量格视图 + 时段/星期分布 + 记录较少的时间 |
| **时间流** | 服用记录与体感事件按时间倒序混排，点任意一条就地改 |
| **数据** | 配色切换、导入 `记录.md`、导出 JSON/Markdown、从 JSON 恢复 |

「记一笔」是底部通栏按钮，任意页面都能唤起——记录发生在任何时刻，不该要求先切页。

## 数据存在哪

优先 `%APPDATA%\StackIt\db.json`。是**你自己的普通文件**：不会被系统清理、能被别的工具读取、可以随手复制备份。

`%APPDATA%` 写不了时（企业策略、受控文件夹访问、重定向配置等）会**自动依次退到**：

1. 程序所在目录的 `data\`（便携模式）
2. `%LOCALAPPDATA%\StackIt`
3. `我的文档\StackIt`
4. 临时目录 `%TEMP%\StackIt`

数据页顶部会写明**实际用了哪个**——退到备用位置时也会标出来，免得备份时找错地方。
全部写不了时列出每个位置失败的具体原因，而不是只说一句「失败了」。

想固定位置（比如放网盘）设环境变量，设了就只用这一个，不做回退：

```powershell
$env:STACKIT_DATA_DIR = "D:\我的备份"
```

写入是原子的（先写临时文件再替换），断电不会写出半截数据。文件万一损坏，启动时自动备份成 `db.json.broken-<时间戳>` 而不是清空。

## 补记以前吃过的

日期、时段、时间**常驻在面板顶部，不折叠**。

- 翻到过去某天，点品类记下，接着可以改下一天继续补，不用关掉重开
- 选了非今天会在日期旁标「补记」，旁边有「今天」一键跳回
- 日期**不能选到未来**（记录的是已经发生的服用）
- 记错了点底部「撤销」
- **凌晨不靠猜**：00:00–02:59 打开记一笔 → 记成**前一天 · 晚**（标「睡前 · 归昨天」）；
  03:00–05:59 → **今天 · 早**（标「凌晨 · 归今天」）。日期与时段在打开那一刻一次定死，
  界面标注、常吃区、实际写入共用同一个值——`--sheet-test` 用固定时刻 01:30 / 04:00 / 09:00 各测一次

## 改以前的记录

时间流里**点任意一条**就展开编辑器，就地改完就地生效：

- 服用记录：品类、日期、时间、时段、份数
- 体感：类型、部位、补充文字
- 每条都能删，删除要二次确认

改完立刻落盘并重算统计，不设草稿状态。

## 配色

**底色固定，只有强调色不同**，在**数据页**切换，点哪个立刻生效，存在本机。

底色统一用**暖纸灰**（页面 `#F4F1EB` / 卡片 `#FCFAF6` / hover `#F6F2EA`）。六套之间的唯一变量是强调色，
所以是横向比较六个颜色，而不是比六种不同的底色。

| 强调色 | 来源 | 感觉 |
|---|---|---|
| **琥珀**（默认） | Radix `amber` | 像体温、像晨光 |
| 陶土 | Radix `orange` | 手账、印章感，暖而沉 |
| 青 | Radix `teal` | 干净清爽，医疗记录该有的样子 |
| 靛 | Radix `indigo` | 压深的普鲁士蓝，冷静专业 |
| 紫 | Radix `violet` | 有辨识度，不落俗套 |
| 苔 | Radix `lime` | 自然但不土 |

强调色取自 [Radix Colors](https://www.radix-ui.com/themes/docs/theme/color) 官方 12 级色阶，不自造；
底色在 UI 重设计时统一换成暖纸（原 Radix `slate` 冷灰与琥珀不同温）。

删除确认色（红）是全局语义，不跟着强调色走。

### 为什么底色要固定

第一版每套连底色一起换，结果是四套不同质的灰：sand 和 gray 在浅色区几乎重叠，
唯一的差别（12 号墨色）又被对比度校正抹平，于是两套肉眼无法区分。
底色统一之后，比的才是颜色本身。

## 关键设计

**两种空白含义不同**，这是本产品的诚信底线：
没有格子/没有带 = 那时还没开始记这一项；有格子但空着 = 记了但那次空着。
前者绝不能画成 0，也不标注「已停」。

**效果记录只做时间对齐，不做因果判断**。时间流页常驻文案「是否相关由你判断」，不输出任何相关系数或 p 值。

**数据真源是导出文件**，`db.json` 是工作副本。数据页顶部常驻提示，请偶尔导出。

## 品类命名

按你的要求用全名：`复合维生素B`、`复合钙`。

归并依据来自数据（勿随意合并）：
- `复合` / `复合2` → **复合维生素B**：81 次中 74 次与 B2/B6 同格，是与它们并列的独立品
- `复合钙` → **复合钙**：与 D3 同格，属钙类，不可并入 B 族
- `复合维生素` / `复合维生素2` → **复合维生素**：与鱼油/PS 同格，属多维

## 导入器与回归验证

`native/StackIt.Core/Importer.cs`，用真实 `记录.md` 验证：

```
✓ 127 周解析成功，周一命中 127/127
✓ 日期修正 = 且仅 = 行 1747/1776/1805（off-by-one 笔误）
✓ 事件 = 1697，无时间条目 = 4（落 precision:'day'，不参与时段分布）
✓ 0 条静默丢弃（未识别 token 进报告）
```

**年份如何确定**：数据只有 `MM-DD` 没有年份。用「每张周表起始日必须是周一」作约束反推，
127 周中 124 周完美匹配；剩下 3 周是连续相邻的 off-by-one 笔误，修正后 127/127 通过。
跨度 **2023-12-25 ~ 2026-09-07**。

### 对拍

解析器与统计算法是从 TypeScript 版 1:1 移植的。「看起来对」不等于「对」——
一个 off-by-one、少一条边界记录、或者星期索引搞错（0=周日 vs 0=周一），
界面上的数字就会悄悄错。

所以拿网页版跑真实 `记录.md` 的结果当黄金基准（`verify/baseline-*.json`，共 21 项检查）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File verify/native.ps1
```

覆盖 1697 条事件逐条比对（不许多、不许少）、统计（总数/天数/日期区间/每品类次数天数覆盖率/星期时段分布）、
分桶（142 周的每周累计与每个品类的可记窗口）。

网页版已删除，基准作为黄金文件保留——它证明的是「C# 移植没有抄错」。

> 改 `记录.md` 或解析逻辑后基准**不会自动更新**。那说明确实变了：
> 先确认变化是对的，再手工同步基准，别为了让验证变绿而改基准。

> 基准文件本身是个人数据（aseline-events.json 就是 1697 条逐条记录），
> 所以 记录.md 与 erify/baseline-*.json 都在 .gitignore 里、只存在于本机。
> 两个后果：① 新克隆的仓库跑不了这个回归，需要自己放一份 记录.md；
> ② 基准是已删除的网页版**唯一**的输出，不可再生。两者都只有本机这一份——这是 2026-10-15 明确确认过的取舍（接受磁盘故障即全丢），不是漏掉的待办。

### 界面耗时

数据一致性全部通过，界面照样可能卡死——数字都对，就是点不动。
所以同一个脚本还会量三个页面的构建耗时，分开记「构造」和「布局」：

```
  stats     热  构造      6 ms   布局      24 ms   合计     30 ms
  timeline  热  构造    288 ms   布局      84 ms   合计    372 ms
  data      热  构造      0 ms   布局      10 ms   合计     10 ms
```

**WPF 的时间几乎总在布局，不在构造。** 时间流最初把 543 天 1697 行全部实例化，
构造只要 279ms，布局却要 **9.4 秒**（占总耗时 97%），界面等于卡死。
不分开量就会去优化错的地方。

现在时间流用 `VirtualizingStackPanel`（`ListBox` + `Recycling` + `ScrollUnit=Pixel`），
并且**日块是懒建的**（`LazyDay`：到第一次测量才建可视树）。

「用了虚拟化」不等于「只构造视口内的项」——这是两个不同的开销。上一版在 `for` 循环里
直接调 `DayBlock()` 把 543 个日块全 new 出来，虚拟化只免掉了离屏项的测量与排版，
构造照样吃掉 **955ms**（时间流打开慢的真正原因）。套上懒容器之后：
构造 6ms、布局 96ms，合计 **1136ms → 102ms**。

超过预算脚本会失败退出：

| 页面 | 预算 |
|---|---|
| 统计 | 1500 ms |
| 时间流 | 3000 ms |
| 数据 | 1500 ms |

### 时间范围筛选

时间流有 543 天、1697 条。**这里做的是筛选，不是分页。**

分页解决的是「一次加载太多」，而这个问题上一节已经用虚拟化解决了（9.4 秒 → 0.1 秒）。
剩下的痛点是**找不到那条记录**——543 天按什么粒度分页都不自然，翻页只是把
「滚很久」换成「点很多次下一页」。筛选直接缩小范围，是更短的路径。

筛选条固定在列表上方（不跟着滚），两级：

```
全部 1697   2026 587   2025 730   2024 355   2023 25
9月 42   8月 103   7月 125   6月 71   5月 26   4月 108 ...
只看 2026-07 · 125 条（全部 1697 条）
```

- 只列出**库里真有数据的**年月，空的不占按钮
- 每个按钮带条数，不用点进去才知道是空的
- 筛选中时显示一行 `只看 X · N 条（全部 M 条）`：用户在别处补记了一条，
  回到时间流可能看不到，这行负责解释为什么

**为什么没有「近 30 天」这类相对范围**：用户是**补记**数据的，库里最新一条未必是今天
（实测某天 2026-10-12，数据止于 2026-09-07）。按墙上时钟算的「近 30 天」会一条都筛不到，
等于给用户一个死按钮。年 / 月的绝对范围没有这个坑。

筛选逻辑（日期前缀匹配，年 vs 月只差几个字符、周要按周一归属）是「少一条 / 多一条」
那类会静默出错的逻辑，所以有断言守着，也进回归脚本：

```powershell
native\dist\StackIt.App.exe --filter-test   # 筛选自检，24 项
```

取值有四种：`all` / `y:2026` / `m:2026-07` / `w:2026-07-06`（值里存的是**周一日期**，
不另外编码周序号——存日期省一次解析，也不会在跨年时和 ISO 周对不上）。

周筛选的坑：**周日属于上一周**。按周一归属，所以 `w:2026-07-13` 覆盖 13~19 日，
7-12 不在内。判不出合法周时**当不过滤**，不能把数据全滤没。

**每个筛选档位都要真渲染一遍**（回归里有）。绘图视图的越界崩溃只在**那个档位**
下才发生 —— 曾经全量视图整个崩溃（`Index was outside the bounds of the array`），
而逻辑自检全绿，因为自检只验日期匹配、不碰绘图代码。只测「全部」也是漏的，
出事的是月 / 周。

### 每周用量（格视图）

**带视图已删除。** 同一个形状没能同时在三种跨度下成立：142 周挤成一条看不出疏密；
缩到 4~5 周又铺满成一片等宽色块；单周时每样只剩一根柱子，信息归零。
格视图在三种跨度下都成立，因为它是"格子"而不是"连续形"。

**格子宽度必须从容器实际宽度算**，不能拿常量。这里踩过两次：

1. 固定 11px → 142 周要 1562px，460 的窗口只露出前 31 周，剩下 4/5 的品类
   在横向滚动条外，看起来整片空白；
2. 改成常量 420 再算 → 忘了减掉左侧 84px 品名列，也没考虑窗口可变宽
   （MinWidth=380）。每行实际 719px，多出来的被滚动条吃掉。

两次都是"画了但看不见"—— 低频品类（维生素B2 有 104 条记录）整行看着像空白。
所以宽度从 `SizeChanged` 量出来，且只在宽度真变了（差 > 1px）时才重排 ——
重排要重建 17 行 × 142 格，每次 SizeChanged 都做会卡顿，而它在布局时连着触发好几次。

**深浅是显式的单色明度渐变**，不复用 `Line` / `Accent` 那些界面颜色。两个原因：

- `Theme.Line` 是 RGB(224,225,230)，跟卡片底 RGB(252,252,253) 只差 28，
  在 4px 小格上等于没画。之前「1 次」用了它，结果所有低频品类整行隐形；
- 深档跳到 `Ink` 之后色相整个变了，读起来像换了语义而不是变深。

色阶由强调色在 HSL 里生成，明度按固定间隔铺开（0.88 → 0.27）而不是相对 Accent 的比例 ——
否则换成深色强调色（靛）时整条色阶挤在暗部，浅档全看不见。

**0 次单独一档且画成空心描边**：它是"记了但那周没吃"，和"没这一列"
（完全空白）必须一眼分得开。实心的浅色块会被读成"吃得很少"。

深浅分 7 档（0 / 1 / 2 / 3~4 / 5~6 / 7~9 / 11+）。实测这份数据每周次数落在 1~11，
原来只分 4 档，绝大多数格子全落在同一个最深档里，看上去一片同色。

统计页共用同一份筛选状态：在统计页选了「2026 年」，切到时间流仍然是 2026 年。
筛选分三层：**年 → 月 → 周**，选中月才出现周行（周的原生刻度就是这份数据的刻度）。

**格视图不能用筛过的库重算**，这是这个功能最容易做错的地方。
`History.Build` 是从传入数据推算每个品类的**可记窗口**（首周→末周）。只喂 2026-07 的数据，
所有品类的窗口都会塌缩成那一个月，格视图就会声称「锌 2026 年 7 月才开始记」——而它其实记了 488 次。
那正是本产品明确禁止的谎：空白分两种（那时记录表还没有这一列 / 记了但那周空着），
塌缩会把两者混成「已停」。

所以做法是：**用全量数据算出真实窗口和完整时间轴，只把范围外的周清零**（`HistoryCalc.BuildRange`），
并且**只绘制可见范围的那些周**（坐标按可见范围走，数据仍用全量）。
聚合数字（次数 / 天数 / 时段 / 星期）用筛过的库，因为它们本来就该只看所选范围。

范围外**不画**（留白），而不是画成 0 厚度发丝 —— 那条发丝会被读成「当时在吃、只是吃少了」，
是另一种谎。窗口说明文字也跟着变，明确「左右两端被截掉不代表停用」。

## 托盘与图标

点右上角关闭 = **收进托盘**，不是退出。记录类工具最常见的用法就是开着窗口记一笔、关掉、
继续过日子；退出应该是明确动作，不是顺手一点。

- 托盘图标：单击或双击都叫回窗口；**右键只弹菜单，不会把窗口叫出来**
  （单击也响应：用户找不到图标时会去点，单击无反应会让人以为图标不存在）
  右键这一刀必须挡：WinForms 的 `NotifyIcon` 右键时会依次抛
  `MouseDown(Right) → MouseUp(Right) → Click`，而 `ContextMenuStrip` 是自己在
  `MouseUp` 里弹出来的 —— 不在 `Click` 上分辨按键，窗口就会正好盖在刚弹出的菜单下面。
  （`--tray-test` 只验证代码路径：本机没有通知区域时它自己就声明「不作为托盘可用的证据」，
  所以右键的实际手感只能在有 explorer 的桌面上确认。）
- 第一次隐藏时弹一次气泡，说明程序没退出
- 真退出的地方只有一个：`MainWindow.Quit()`

### 托盘注册会静默失败

`NotifyIcon.Visible = true` 要经过 Explorer（`Shell_NotifyIcon` 往它的通知区域塞图标）。
**没有 explorer.exe 的环境**（服务、沙箱、部分远程会话、远程桌面断开后）
注册会**静默失败**：不抛异常、不打日志，图标只是永远不出现。
所以 `SetupTray()` 设完立刻回读 `TrayRegistered`，失败就走另一条路。

**注册失败时不能藏窗口。** 藏了用户就没法再打开，只能去任务管理器杀进程，
数据还没存就丢了。这种情况下直接退出，并弹窗说清楚原因。

```powershell
native\dist\StackIt.App.exe --tray-test
```

自检会打印本机有没有 explorer、托盘有没有注册上 —— 没有通知区域时它只验证代码路径，
不作为「托盘可用」的证据。

**用户看不到图标时用 `--tray-diag`**，它不是断言，是把每一层的真实状态打印出来：

```powershell
native\dist\StackIt.App.exe --tray-diag
```

依次查：explorer 进程数、本进程会话号、四个通知区域窗口在不在（`Shell_TrayWnd` /
`NotifyIconToolbarWindowClass` / `TrayNotifyWnd` / 副屏）、实际注册结果、图标颜色数。
每一层都正常但用户仍看不到，只剩这几种：通知区域被设成「永不显示」、图标收在「^」折叠区、
程序已经关了、多显示器跑到副屏上了。

注意 `Console.OutputEncoding` 在输出被重定向时会抛 `IOException`（GUI 子系统没有真
控制台），所以那条要 try 包起来 —— 否则诊断命令自己先崩了。

两个必须显式处理的坑：

1. **`ShutdownMode` 必须是 `OnExplicitShutdown`**。默认的 `OnLastWindowClose` 会在最后一个
   窗口关闭时结束程序 —— 那样「隐藏」和「退出」根本没法区分，而且不留任何报错。
2. **`NotifyIcon` 必须显式 `Dispose()`**，否则托盘图标会残留到你手动重启 Explorer。

自检跑在 `SuppressDialogs` 下：不弹任何对话框。`MessageBox` 会阻塞等输入，
自动化跑起来就是一个**永远不返回的进程** —— 表现为「回归脚本卡在这一步不动」，
而不是干脆地失败。这个坑踩过一次。

### 图标

图标由 `IconGen.cs` 用代码画出来，不是提交一张二进制图 —— ICO 看着看不出画了什么，
改也只能靠猜。形状是四根高低不一的柱子（记录密度）。

```powershell
native\dist\StackIt.App.exe --make-icon native\StackIt.App\app.ico
native\dist\StackIt.App.exe --icon-test native\StackIt.App\app.ico
```

**底色用 `Accent` 而不是 `AccentDeep`。** 踩过：用户反馈「exe 图标全黑」。
`AccentDeep` 是色阶里的深棕档（琥珀色下就是 RGB 79,52,34），设计用途是
「深底承载文字」，当图标底色就成了看不出图案的黑饼。`--tray-test` 里有一条
断言专门守这个：图标中心像素亮度不能低于 60。

**小尺寸必须是单独一套形状**，不能只把大图缩小：圆角在 16px 上只剩锯齿，
柱子之间的缝直接糊掉。所以 ≤32px 走直角、柱子更宽、留白更小（`Draw(size)`）。

五个坑（都踩过，其中前两个会让图标**静默变空白**）：

1. **绘制坐标要按比例缩放**。`Draw()` 里坐标是按 256 画布写的绝对值，直接渲染成 16x16
   的位图时只有左上角 16x16 单位被画到 —— 那正好是圆角透明的角，于是小尺寸整帧全透明。
   必须先 `ScaleTransform`。
2. **ICO 目录的 offset 要一次写对**。目录在文件前部、数据在后面，所以写目录时就得知道
   每项多大。一边写一边累加偏移，累加结果没机会写回去 —— 所有项的 offset 会都等于第一项，
   Windows 挑那个唯一真实存在的 256 尺寸凑合显示（任务栏看着正常），
   而小尺寸取到越界数据，图标一片空白。
3. **ICO 里存 PNG 是 Windows 认、WPF 不认**。Vista 起允许直接存 PNG 整块，资源管理器正常，
   但 WPF 的 `BitmapDecoder` 会抛 `FileFormatException`。所以手写 32 位 BMP（DIB）条目。
4. **图标必须建成 `Resource`**（XAML / pack URI 按资源找），不能只 `None`。
5. **托盘图标不能只存在局部变量里**。`Icon` 包着一个 HICON，方法一返回局部变量就成了垃圾；
   GC 回收时 HICON 被销毁，**托盘上的图标变成空白** —— 现象正好是「托盘没有图标」，
   而且不崩不报错。所以存成 `_trayIcon` 字段活到 `Quit()` 才释放。

前两条不会崩、不会报错，只会让图标在某些地方变空白，所以 `--icon-test` 断言两件事：
每个目录项的区间都落在文件内且**偏移互不相同**，以及 16px / 32px **真的能解出多种颜色**
（纯色 = 没画出来）。

`<ApplicationIcon>` 得先有文件才能 build，而生成器就是这个 exe —— 鸡生蛋。
所以 `app.ico` 留在项目里当生成物，要从头来先把这行注释掉 build 一次。

`app.ico` 同时是 `Content` 复制到输出目录，好让自检能按路径读同一份文件。

## 代码签名（绕开 SmartScreen）

无签名证书时，Windows 会把 `StackIt.App.exe` 判为「发布者未知」，双击即弹 SmartScreen 拦截。
内部自用无需买证书，用**自签名 + 预装信任**即可消除拦截（快速开始里的 `publish.ps1` 已自动签名）：

```powershell
cd native

# 1. 开发者机器只跑一次：生成证书、装进本机"根" + "受信任的发布者"、导出公钥给同事
powershell -ExecutionPolicy Bypass -File .\new-cert.ps1

# 2. 之后每次发布都用这个（自动 publish 到 native/dist + 签名）
powershell -ExecutionPolicy Bypass -File .\publish.ps1
#    自包含单文件：.\publish.ps1 -SelfContained
#    本机连不上 nuget.org：.\publish.ps1 -NoRestore
```

内部同事每台装一次公钥（`StackIt-CodeSign.cer`，需管理员 PowerShell）：

```powershell
Import-Certificate -FilePath StackIt-CodeSign.cer -CertStoreLocation Cert:\LocalMachine\Root
Import-Certificate -FilePath StackIt-CodeSign.cer -CertStoreLocation Cert:\LocalMachine\TrustedPublisher
```

> 自签名只对**装了该根证书的机器**有效；发给外部陌生人仍会被拦截——
> 那种情况要么买 EV/OV 代码签名证书，要么走 MSIX 上架 Microsoft Store。
> `StackIt-CodeSign.cer` 已在 `.gitignore` 中，不会入库。

## 已知约束

- **列结构随时间扩展**，不是收缩：3列(2023-12) → 4列(+米诺地尔) → 5列(+二硫化硒) → 6列(2026-02 加「其他维生素」)。
  因此 D3/鱼油/镁/PS/E/A **在 2026-02 之前无列可记**，其「最后一次出现」**不等于停用日期**。
- 品类状态只显示「记录区间」，不显示「已停」。
- 发布物是 folder 发行（8 个文件，约 1.8 MB），目标机器需装 .NET 8 Desktop Runtime。
  引了 WinForms 只是为了 `NotifyIcon`，但会把整个 WinForms 拖进来，exe 从 148 KB 涨到 512 KB。
  要免安装的单文件 exe，在能联网的机器上跑 `dotnet publish -c Release -r win-x64 --self-contained`。
- **托盘图标只在有通知区域的交互式桌面会话里可用。** 服务、沙箱、部分远程会话下
  注册会静默失败，此时点关闭直接退出（见上文）。
